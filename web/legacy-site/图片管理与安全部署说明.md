# 图片管理与安全部署

## 两种 ESP32-P4 上传模式

两种模式均使用同一个接口：`POST /api/process.php`，请求体仍是 JPEG 原始二进制，并携带既有的 `X-Device-Token` 与 `X-Member-Id`。

| 设备操作 | 新增请求头 | 云端状态 | 是否自动运行模型 |
| --- | --- | --- | --- |
| 上传图片保存 | `X-Upload-Mode: archive` | `saved` | 否 |
| 云端检测 | `X-Upload-Mode: detect` | `received` | 是 |

`X-Upload-Mode` 未传时，为兼容旧固件，默认按 `detect` 处理。设备端只有在收到 HTTP `201` 且 JSON 中 `ok: true` 后，才能把本地图片标记为上传完成。

保存模式成功响应示例：

```json
{
  "ok": true,
  "detection_id": "...",
  "upload_mode": "archive",
  "status": "saved",
  "message": "图片已保存，可在网页端选择云端分析。"
}
```

网页“影像管理”页可按成员和图片类型筛选。保存图片会显示“云端分析”按钮；点击后才会被模型工作进程领取。所有记录都支持预览、下载和删除。删除会连同该图片的模型结果一并删除，无法恢复。

## 首次升级：执行数据库迁移

在 phpMyAdmin 中选中本站数据库，执行一次：

`database_image_management_migration.sql`

它会为旧的 `detections` 表增加 `upload_mode`，并为“仅保存”增加 `saved` 状态。旧记录默认标记为 `detect`，不会影响既有历史。

## 防止更新代码时丢失图片

新代码将图片保存到站点目录外的默认位置：

```text
/www/wwwroot/chijing_storage/history/
```

因此后续可随时替换 `/www/wwwroot/8.138.230.100_667/` 内的网站代码，历史图片不会被覆盖。升级前在服务器执行：

```bash
SITE_ROOT=/www/wwwroot/8.138.230.100_667
STORAGE_ROOT=/www/wwwroot/chijing_storage

mkdir -p "$STORAGE_ROOT/history" "$STORAGE_ROOT/latest"

# 若存在旧版图片，先复制；不要先删除旧 data/history。
if [ -d "$SITE_ROOT/data/history" ]; then
  rsync -a "$SITE_ROOT/data/history/" "$STORAGE_ROOT/history/"
fi

# 宝塔常见 PHP 运行用户为 www；若你的站点用户不同，请替换为实际用户。
chown -R www:www "$STORAGE_ROOT"
chmod -R u+rwX,g+rwX,o-rwx "$STORAGE_ROOT"
```

新代码会优先读取旧位置 `data/history/...`，再读取新的外部目录，所以旧记录在复制完成后仍能预览。确认网页历史图片可正常预览后，旧的 `data/history` 可保留为备份；不要将其打包进后续代码压缩包。

若宝塔 PHP 使用的不是 `www` 用户，请在宝塔“网站 → 运行目录 / PHP”或服务器进程中确认用户后，再执行对应的 `chown`。上传失败通常是外部存储目录没有写权限，而不是 ESP32 请求格式问题。

## 推荐的后续部署方式

1. 先备份数据库与 `chijing_storage` 目录。
2. 上传并解压新代码到站点根目录，但不要删除外部的 `chijing_storage`。
3. 执行本次数据库迁移。
4. 按上面的命令创建并授权外部存储目录、复制旧图片。
5. 用网页预览一张旧图片，再从 ESP32 上传一张“保存模式”图片验证。
