# 齿镜服务器图片上传故障修复说明

> 编写日期：2026-07-22  
> 适用站点：`/www/wwwroot/8.138.230.100_667`  
> 对应本地工程：`D:\Projects\WebProject\齿镜快速部署版`

## 1. 故障现象

ESP32-P4 已成功连接 Wi-Fi、取得 DHCP 地址并完成 JPEG 编码，请求也能到达服务器，但设备侧收到：

```text
HTTP response: mode=archive status=200 bytes=329 accepted=false
[HTTP DIAG] transport=ESP_OK content_type=html status_events=1 redirect=no
json_object=no ok=missing upload_mode=missing status=missing
```

按照图片推送接口约定，正常归档响应应为 HTTP 201 和 JSON：

```json
{
  "ok": true,
  "upload_mode": "archive",
  "status": "saved"
}
```

因此，设备收到 `text/html` 说明服务器没有执行到正常 JSON 成功响应。

## 2. 已确认根因

服务器公开的 `/api/system_status.php` 返回：

```text
open_basedir restriction in effect
/www/wwwroot/chijing_storage 不在 PHP 允许访问的路径中
Fatal error: Storage directory unavailable
```

相关调用链：

```text
api/process.php
  ↓ 调用 ensure_storage()
api/config.php
  ↓ 默认使用 /www/wwwroot/chijing_storage
PHP open_basedir
  ↓ 只允许站点目录和 /tmp
输出 HTML Warning/Fatal error，无法返回接口规定的 JSON
```

当前 `open_basedir` 允许范围类似：

```text
/www/wwwroot/8.138.230.100_667/:/tmp/
```

但图片目录位于：

```text
/www/wwwroot/chijing_storage/
```

所以即使 Linux 文件权限正确，PHP 仍会拒绝访问。根因位于服务器目录隔离配置，不是 ESP32、Wi-Fi、JPEG 或成员请求格式。

## 3. 推荐修复方案：保留站点外部图片目录

该方案可以避免以后更新网站代码时误覆盖历史图片，是正式部署的推荐方式。

### 3.1 备份现有数据

修改前先在宝塔或服务器终端备份：

- 站点数据库；
- 站点内原有的 `data/history`；
- 已存在的 `/www/wwwroot/chijing_storage`。

不要先删除旧图片目录。

### 3.2 创建外部存储目录

在服务器终端执行：

```bash
mkdir -p /www/wwwroot/chijing_storage/history
mkdir -p /www/wwwroot/chijing_storage/latest
```

确认 PHP-FPM 实际运行用户。宝塔常见用户是 `www`，但应以服务器实际配置为准：

```bash
ps -eo user,comm | grep -E 'php-fpm|php-cgi'
```

如果运行用户确实为 `www`，执行：

```bash
chown -R www:www /www/wwwroot/chijing_storage
find /www/wwwroot/chijing_storage -type d -exec chmod 770 {} \;
find /www/wwwroot/chijing_storage -type f -exec chmod 660 {} \;
```

不要直接使用 `chmod -R 777`。

### 3.3 修改宝塔 open_basedir

在宝塔站点设置中找到“防跨站攻击（open_basedir）”或对应 PHP 目录限制，将外部目录加入允许列表。

修复后的允许范围应包含：

```text
/www/wwwroot/8.138.230.100_667/:/www/wwwroot/chijing_storage/:/tmp/
```

如果宝塔通过站点根目录下的 `.user.ini` 管理该配置，应确保其 `open_basedir` 同样包含上述外部目录。不要删除原有站点目录和 `/tmp/`。

修改后重载对应版本的 PHP-FPM，或通过宝塔面板重启 PHP 服务。

## 4. 修复服务器诊断接口

当前 `api/system_status.php` 还使用了已经不存在的 `DATA_DIR` 常量。存储目录权限修复后，这一处会成为新的 PHP 错误。

建议将该文件调整为始终返回 JSON，并使用 `storage_root()`：

```php
<?php
declare(strict_types=1);
require_once __DIR__ . '/config.php';

try {
    ensure_storage();
    db()->query('SELECT 1');
    json_response([
        'ok' => true,
        'service' => 'chijing-quick',
        'time' => date(DATE_ATOM),
        'database' => true,
        'storage_writable' => is_writable(storage_root()),
    ]);
} catch (Throwable $e) {
    error_log('system status check failed: ' . $e->getMessage());
    json_response([
        'ok' => false,
        'service' => 'chijing-quick',
        'database' => false,
        'storage_writable' => false,
        'error' => 'Server storage or database is unavailable.',
    ], 500);
}
```

建议同时在 `api/process.php` 中捕获存储初始化异常，确保以后配置错误时向 ESP32 返回 JSON 500，而不是 HTML 错误页：

```php
try {
    ensure_storage();
} catch (Throwable $e) {
    error_log('upload storage initialization failed: ' . $e->getMessage());
    json_response([
        'ok' => false,
        'error' => '图片存储服务暂不可用。',
    ], 500);
}
```

这项异常处理只能改善错误响应，不能代替第 3 节的目录与 `open_basedir` 修复。

## 5. 服务器验证

### 5.1 验证状态接口

```bash
curl -i http://127.0.0.1:667/api/system_status.php
```

预期结果：

```text
HTTP/1.1 200 OK
Content-Type: application/json
```

响应中应满足：

```json
{
  "ok": true,
  "database": true,
  "storage_writable": true
}
```

如果仍出现 `open_basedir restriction in effect`，说明宝塔配置尚未生效或 PHP-FPM 没有重载。

### 5.2 验证接口路由

```bash
curl -i http://127.0.0.1:667/api/process.php
```

因为该请求不是 POST，预期返回 HTTP 405 JSON：

```json
{
  "ok": false,
  "error": "POST required"
}
```

此步骤不上传图片，也不需要设备令牌。

### 5.3 使用 ESP32 验证归档模式

设备点击 `UPLOAD TO CLOUD` 后，串口应出现：

```text
HTTP request: mode=archive member_kind=cloud JPEG bytes=<实际大小>
HTTP response: mode=archive status=201 bytes=<响应大小> accepted=true
[HTTP DIAG] transport=ESP_OK content_type=json status_events=1 redirect=no json_object=yes ok=true upload_mode=archive status=saved detection_id=present member_id=present error_class=none
```

随后到网页端确认新图片已归入所选成员，且没有自动进入模型检测队列。

### 5.4 使用 ESP32 验证检测模式

设备点击 `START DETECTION` 后，预期：

```text
HTTP response: mode=detect status=201 ... accepted=true
[HTTP DIAG] ... ok=true upload_mode=detect status=received ...
```

随后确认模型服务能够领取 `received` 状态任务。

## 6. 临时替代方案

如果当前无法修改宝塔 `open_basedir`，可以暂时将图片根目录放回站点允许范围内，例如将 `storage_root()` 的默认值改为：

```php
$root = rtrim(
    $configured !== '' ? $configured : APP_ROOT . '/data',
    '/\\'
);
```

并确保站点内目录可写：

```bash
mkdir -p /www/wwwroot/8.138.230.100_667/data/history
mkdir -p /www/wwwroot/8.138.230.100_667/data/latest
chown -R www:www /www/wwwroot/8.138.230.100_667/data
```

该方案部署简单，但以后覆盖或重新解压网站文件时必须保护 `data/`，否则可能丢失历史图片。因此只建议临时使用。

## 7. 常见结果判断

| 现象 | 含义 | 处理 |
| --- | --- | --- |
| `content_type=html`、`json_object=no` | PHP/Nginx/WAF 输出了 HTML | 查看 PHP 错误日志和 `open_basedir` |
| HTTP 500 JSON、`error_class=server` | 服务器已正确返回结构化错误 | 检查存储、数据库和 PHP 日志 |
| HTTP 401 JSON | 设备令牌失效或设备已解绑 | 在网页重新绑定设备 |
| HTTP 409/422 JSON | 没有可用成员或成员已失效 | 同步成员并重新选择 |
| `member_kind=local-pending` | 使用了未同步到云端的本地成员 | 先解决成员同步冲突 |
| HTTP 201、`accepted=true` | 上传接口契约完全匹配 | 再检查网页归档或模型队列 |

## 8. 安全注意事项

- 不要把数据库密码、设备 Token、模型回调密钥写入本文、串口日志或公开仓库。
- 不要打印完整上传响应；设备只记录经过白名单分类的诊断字段。
- 如果凭据曾出现在聊天、终端输出、截图或提交记录中，应立即轮换。
- 修改目录权限时遵循最小权限原则，不使用全局可写的 `777`。
- 部署新代码前同时备份数据库和外部 `chijing_storage`，不要只备份网站目录。

## 9. 本次故障结论

本次上传失败由服务器 `open_basedir` 阻止 PHP 访问 `/www/wwwroot/chijing_storage` 引起。ESP32 已正确完成联网、JPEG 编码和 HTTP POST；在服务器目录白名单和写权限修复前，不应继续修改板端上传协议，也不应把 HTTP 200 HTML 错误页放宽为上传成功。
